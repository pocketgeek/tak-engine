# Crusades drake death after lobby registry replacement

Reported match: checkout Release client, Zhon versus passive Aramon, Ulasem
Arena, Crusades balance. Local recording:
`game-1-1789949738.takrep` (77,671 bundles, protocol 171).

The first bad saved checkpoint is tick 77,550. An Aramon archer (170) kills
drake 371 at tick 77,549. Fresh Release and optimized Debug simulations agree
throughout the replay; enabling local visibility makes no difference. They
match every recorded checkpoint before this death.

| Checkpoint | Recorded client | Fresh referee simulation |
| --- | --- | --- |
| 77,520 | `bbfad87a1f9331de` | `bbfad87a1f9331de` |
| 77,550 | `84a41022e1dcd456` | `4851f2f886ac74c2` |

The drake has no corpse definition. Changing only its `corpseUntil` from 120
to `INT32_MAX` reproduces the recorded bad checksum exactly.

The client constructor registers features before the lobby starts its match.
Changing balance or override policy replaces the unit registry. Corpse, stone,
and frozen mappings are keyed by unit-type address, but neither authoritative
feature rebuild nor replay reset cleared those mappings. An allocator can reuse
an old corpse-bearing unit's address for a corpse-less unit. Registration only
writes present definitions, leaving the stale mapping in place.

An isolated replay probe seeded that stale drake mapping before `setupMatch`.
With the old code it reproduces **every recorded checkpoint**, including the
bad final checkpoint. This is an injected stale-state reproduction; allocation
reuse itself depends on the live client's allocation history.

The fix clears the feature table and all three unit-type mappings together on
authoritative feature rebuild, standalone registration, and replay reset.
Fresh-match simulation behavior and pathfinding are unchanged. No protocol
bump is needed: this restores the client's initialization to the existing
referee behavior.

`featgen_test` covers all three reset paths and compares a corpse-less unit's
death against a fresh world. All six new assertions fail against the old code
and pass after the fix. Scratch evidence lives in
`/tmp/tak-corpse-test-before.log`, `/tmp/tak-corpse-focused-test.log`, and
`/tmp/tak-drake-stale-{before,after}.log`.

An unmodified recording still contains the original client's bad final hash;
corrected replay verification must report that historical mismatch, rather
than treating the bad recorded corpse lifetime as authoritative.

Validation after the fix:

- All targets rebuilt in Release, Debug, and optimized Debug; 37/37 CTests pass
  in each configuration.
- Corrected stale-initialization replay matches the fresh referee at all 169
  logged ticks, including every tick from 77,510 through 77,670.
- Native GCC/Clang O0/O2/O3 deterministic-math checks agree on
  `8adc4762a852fadd`; the ARM cross-build is unavailable (missing headers).
- Two seeded Crusades client/server smoke runs both finish at tick 600 with
  hash `b879f25ebe4532bf`, no desync, and exit 0.
- The separate Ctrl+Z change was exercised through the rebuilt Debug client's
  key handler: selecting two types expands to four owned units of both types,
  excluding an enemy of a matching type. The test uses a controlled render
  snapshot in GDB (`/tmp/tak-mixed-selection-expanded.gdb`).
